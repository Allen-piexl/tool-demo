Building Booking Primitives

Tutorial — LLM-backed browser workflow primitive

LLM primitive tool use browser automation workflow state intermediate

What you will learn

  • How a booking primitive differs from a simple API primitive like stock lookup
  • How to split the primitive into LLM planning, API search, session state, and browser execution
  • How to let the LLM handle user language while deterministic code handles fragile checkout pages
  • How to ask the user only when the workflow reaches a real confirmation or missing field
  • How to design your own booking-style primitive for another website

What is a Booking Primitive?

A booking primitive is an LLM-backed tool primitive that does more than call one API. It converts a natural-language travel request into structured flight search arguments, calls a flight search backend, opens a live checkout session, collects missing passenger information, and drives the checkout page until it reaches payment or a user decision point.

It still has the same basic shape as a simple primitive:

text
User message
  -> LLM extracts structured intent
  -> Tool/API call
  -> Structured result
  -> Natural-language answer

The difference is that booking is a stateful workflow. Searching flights is one turn. Completing checkout takes many turns, and each turn depends on the live browser state.

Key idea A booking primitive should not make the LLM click random page elements. Use the LLM for language understanding and decision normalization. Use deterministic browser code for selectors, field filling, and repeatable page transitions.

The core observation

Most booking flows share the same computational pattern even when the website changes:

Stage What happens Who should handle it?
Intent extraction User says where, when, how many passengers, and whether it is one-way or round-trip. LLM
Inventory lookup Search API returns available options and booking URLs. API tool
Checkout opening Browser opens the selected booking URL and detects the current step. Browser actuator
Information collection User provides names, nationality, DOB, email, phone, and other required fields. LLM plus session state
Form execution Fields are filled, add-ons are skipped, and the page advances. Deterministic Playwright code
User confirmation Price increases, payment, or ambiguous choices require explicit user approval. User

The primitive is useful because it packages this pattern behind a clean interface. The frontend does not need to know how Kiwi's passenger page works. It only sends messages to the primitive and receives a structured session response.

Architecture

The LLM contract

The primitive uses two separate LLM prompts. Keeping them separate makes the workflow easier to debug.

1. Search planner

The search planner converts a user travel request into a tool decision.

jsonplanner output
{
  "decision": "use_tool",
  "tool": "search_oneway",
  "question": "",
  "answer": "",
  "args": {
    "origin": "SEA",
    "destination": "JFK",
    "date": "2026-06-12",
    "adults": 1,
    "cabin_class": "ECONOMY",
    "currency": "usd"
  }
}

The planner can also return ask_user when the origin, destination, date, or trip type is missing. This keeps incomplete searches out of the tool layer.

2. Passenger extractor

After a booking session is open, the user may answer one field at a time or provide a whole sentence. The passenger extractor turns that message into a patch.

jsonpassenger patch
{
  "passenger_patch": {
    "given_name": "Alex",
    "surname": "Chen",
    "nationality": "CN",
    "gender": "male",
    "dob_day": "09",
    "dob_month": "10",
    "dob_year": "1997",
    "email": "alex@example.com",
    "phone": "+1 5550101234"
  }
}
One-value replies If the primitive asks "What is the passenger's surname?" and the user replies only "Jin", the session state should assign that value to the current field directly. Do not force users to write structured JSON.

Session model

A booking session stores two things:

  • Collected user data: fields such as name, nationality, DOB, email, and phone.
  • Live browser state: the Playwright page opened at the selected booking URL.

The public session API is intentionally small:

EndpointPurpose
POST /invokeSearch flights from natural language.
POST /sessions/openOpen a selected booking URL and create a browser session.
POST /sessions/{id}/messageProcess a user reply, update collected fields, and advance the booking flow.
POST /sessions/{id}/continueTry to continue from the current browser step.
DELETE /sessions/{id}Close the browser and clear session memory.
Do not trust frontend state The backend session should be the source of truth for collected fields. The frontend may display fields, but it should not overwrite backend session state with stale data.

Browser actuator

The browser actuator is the deterministic part of the primitive. It is responsible for opening the page, detecting the current step, filling fields, clicking predictable buttons, and stopping at real decision points.

Step detection

Do not rely only on page text. Use a combination of DOM selectors and text markers.

pythonstep detection sketch
def detect_step(page):
    text = read_page(page).lower()

    if "price has increased" in text:
        return "confirmation"

    if "pay with" in text or "billing details" in text:
        return "payment"

    if passenger_form_present(page):
        return "passengers"

    if "continue with saver" in text:
        return "fare"

    return "unknown"

Filling fields

For important fields, use exact selectors first and fallback selectors second. After filling, dispatch input/change/blur events so React-controlled fields notice the value.

pythonfield fill sketch
def fill_given_name(page, value):
    loc = page.locator('input[name="passengers.0.firstname"]').first
    loc.scroll_into_view_if_needed()
    loc.click()
    loc.fill(value)
    loc.evaluate("""
      (el) => {
        el.dispatchEvent(new Event('input', { bubbles: true }));
        el.dispatchEvent(new Event('change', { bubbles: true }));
        el.dispatchEvent(new Event('blur', { bubbles: true }));
      }
    """)

Phone numbers

Phone numbers often have two UI controls: country code and national number. Preserve the user's country code, then split it before filling the page.

python
def split_phone(value):
    # "+1 5550101234" -> ("+1", "5550101234")
    match = re.match(r"^\s*(\+\d{1,3})[\s\-().]*(.*)$", value)
    if not match:
        return None, re.sub(r"\D+", "", value)
    return match.group(1), re.sub(r"\D+", "", match.group(2))

Decision points

The actuator should not silently accept every page. Price increases, payment selection, and any expensive add-on should stop and ask the user.

Human confirmation If Kiwi says the price increased from one amount to another, the primitive should ask: "Reply continue to accept the new price, or back to search again." This is not a place for autonomous guessing.

Server skeleton

pythonserver.py
app = FastAPI(title="KiwiBookingPrimitiveModel")

SESSIONS = {}
COLLECTED = {}

@app.post("/invoke")
def invoke(req):
    plan = llm().generate_json(SEARCH_SYSTEM_PROMPT, req.query, req.history)
    args = normalize_search_args(plan["tool"], plan["args"])
    result = call_tool(plan["tool"], args)
    return build_response(result)

@app.post("/sessions/open")
def open_session(req):
    session_id = new_id()
    runner = BookingSessionRunner(req.booking_url)
    status = runner.open()
    SESSIONS[session_id] = runner
    COLLECTED[session_id] = {}
    return session_response(session_id, status)

@app.post("/sessions/{session_id}/message")
def session_message(session_id, req):
    collected = COLLECTED[session_id]
    patch = llm().generate_json(PASSENGER_SYSTEM_PROMPT, req.message)
    collected.update(clean_patch(patch))
    status = SESSIONS[session_id].run(
        lambda s: s.apply_collected_fields(collected)
    )
    status = SESSIONS[session_id].run(lambda s: s.continue_if_possible())
    return session_response(session_id, status)
Threading detail If you use Playwright's sync API inside FastAPI, run all Playwright operations for a session in a dedicated worker thread. This avoids the "Sync API inside asyncio loop" error and keeps each page bound to one execution thread.

Walk-through

  1. User searches for a flight. The frontend sends the user's text to /invoke. The LLM planner selects search_oneway or search_roundtrip and returns structured arguments.
  2. The primitive returns flight options. The flight API parser normalizes price, stops, baggage, legs, and booking URL. The frontend renders each option with a "Book this option" action.
  3. User selects an option. The frontend calls /sessions/open with the selected booking URL. The backend opens the browser and detects the first checkout step.
  4. The primitive asks for missing information. If passenger name, nationality, DOB, email, or phone is missing, the session asks one direct question. The user can answer with a short value or a full sentence.
  5. The browser actuator fills the checkout page. Once required fields are collected, Playwright fills the page, selects no checked baggage, selects no insurance, advances fare and seat steps, and stops at payment or confirmation.
  6. The primitive stops at payment. Payment is a manual step. The primitive should not enter credit card details or click final purchase buttons unless the product explicitly supports that and the user has confirmed.

Build your own booking primitive

The same pattern can be adapted to hotel booking, restaurant reservations, appointment scheduling, or event ticketing.

  1. Define the external intent. Write the fields the LLM must extract: dates, location, number of guests, budget, preferences, and whether follow-up questions are allowed.
  2. Create one tool layer. Implement deterministic functions such as search_hotels, search_slots, or search_tickets. The LLM should choose tools, not call arbitrary URLs.
  3. Normalize results. Return stable fields like option, price, provider, and booking_url.
  4. Model the checkout session. Store collected fields and browser state server-side. Do not rely on frontend state as the source of truth.
  5. Write exact selectors first. Use stable attributes such as name, data-test, autocomplete, and accessible labels before fuzzy text matching.
  6. Define stop conditions. Price changes, cancellation policies, payment, and irreversible actions should ask the user.
  7. Expose a small API. Keep /invoke for search and /sessions/* for the stateful workflow.

Design principles

PrincipleMeaningPractical test
LLM for language The LLM extracts intent, normalizes user replies, and asks follow-up questions. Can users answer naturally instead of writing JSON?
Code for execution Selectors, field filling, and page transitions are deterministic and testable. Can the same collected data produce the same browser actions twice?
Backend-owned state The server stores collected fields and browser sessions. Can a stale frontend render fail without corrupting the session?
Human confirmation The primitive stops when money, policy, or irreversible actions are involved. Does a price increase ask the user before continuing?

Checklist

  • /invoke accepts natural language and returns structured flight options.
  • The LLM planner can ask follow-up questions when required search fields are missing.
  • Flight API parsing returns normalized, frontend-friendly results.
  • Booking sessions are stored on the backend and cleaned up when closed.
  • Playwright operations run in a stable execution context, not directly inside an async event loop.
  • The passenger extractor supports both one-field replies and full-sentence replies.
  • Phone numbers preserve country code and split it from the national number when filling the page.
  • Each browser step has a screenshot and structured status.
  • The primitive stops for price increases, payment, and ambiguous confirmations.
  • Real API keys and user identity data are never committed to the repository.
