Building Booking Primitives

Tutorial — designing an LLM-controlled booking workflow

LLM primitive tool use browser automation workflow state intermediate

What you will learn

  • How to build a primitive where an LLM manages a multi-step booking workflow
  • How the LLM chooses tools, extracts arguments, tracks missing information, and decides when to ask the user
  • How deterministic tools execute the fragile parts: API calls, browser selectors, form filling, and page transitions
  • How to expose a clean primitive interface while hiding the internal booking complexity
  • How to stop safely at user-confirmation, policy, and payment boundaries

What is a Booking Primitive?

A booking primitive is a self-contained LLM-managed workflow unit. It receives a natural-language user request, decides which tools are needed, calls those tools with structured arguments, opens and maintains a live booking session, asks the user for missing information, and advances the workflow until it reaches a stable endpoint such as payment or a user confirmation.

The primitive hides a multi-step process behind a small external interface. A client should not need to know how flight search, passenger forms, baggage choices, insurance pages, price-change confirmations, and payment pages are implemented internally. The client only sends user messages and receives structured primitive responses.

At the highest level, the primitive is an LLM controller wrapped around a tool environment:

text
User message
  -> LLM controller decides the next action
  -> Tool layer performs API or browser action
  -> State store records what changed
  -> LLM/controller decides whether to continue, ask, or stop
  -> Primitive returns answer + structured status

This is why booking primitives are naturally stateful. Searching for options is one step. Completing a booking requires many turns, and each turn depends on both the user's data and the live browser state.

Key idea The LLM manages the workflow, but it should not directly click random page elements. Use the LLM for language understanding, tool selection, field extraction, and decision routing. Use deterministic tools for API calls, selectors, field filling, and repeatable page transitions.

The LLM as workflow controller

The most important design choice is to make the LLM the controller of the primitive, not just a text parser. The controller repeatedly answers one question: given the user message, current collected data, and current workflow state, what should happen next?

A useful controller action space is small and explicit:

ActionMeaningExample
ask_user Required information is missing or a user decision is needed. "What is the passenger's nationality?"
use_tool The primitive has enough information to call a search or browser tool. Call search_oneway with origin, destination, and date.
update_state The user provided information that should be merged into session state. Extract name, date of birth, email, and phone from one sentence.
continue_workflow The browser can safely advance without new user input. Fill passenger form and skip optional insurance.
stop The workflow reached payment, completion, or an unsafe irreversible point. Stop at payment and ask the user to complete payment manually.

The primitive implementation does not have to expose these action names directly to the frontend. Internally, however, this action space keeps the LLM's job narrow and testable.

textcontroller loop
while workflow is active:
  observe user_message + session_state + browser_status
  LLM chooses next action
  if action == ask_user:
      return question
  if action == use_tool:
      call API/search tool
  if action == update_state:
      merge extracted fields
  if action == continue_workflow:
      run deterministic browser actuator
  if action == stop:
      return final status

The workflow pattern

Most booking flows share the same computational pattern even when the supplier, route, and checkout page change. The primitive must interpret user intent, call search tools, maintain session state, execute deterministic UI actions, and stop for user confirmation before risky or irreversible steps.

Stage What happens Who should handle it?
Intent extraction User describes the task in natural language. LLM
Tool planning The primitive chooses which available search or browser tool to call and with which arguments. LLM
Workflow opening Browser opens the selected target page and detects the current step. Browser actuator
Information collection User provides required missing fields or choices. LLM plus session state
UI execution Fields are filled, safe defaults are applied, and the page advances. Deterministic Playwright code
User confirmation Risky, ambiguous, or irreversible actions require explicit user approval. User

The primitive is useful because it packages this pattern behind a clean interface. The frontend does not need to know how the supplier's passenger page, baggage page, or payment page works. It only sends messages to the primitive and receives a structured response describing the current booking state.

Architecture

The LLM contract

The primitive uses two separate LLM prompts. Keeping them separate makes the workflow easier to debug.

1. Search planner

The search planner converts a user travel request into a tool decision.

jsonplanner output
{
  "decision": "use_tool",
  "tool": "search_oneway",
  "question": "",
  "answer": "",
  "args": {
    "origin": "SEA",
    "destination": "JFK",
    "date": "2026-06-12",
    "adults": 1,
    "cabin_class": "ECONOMY",
    "currency": "usd"
  }
}

The planner can also return ask_user when the origin, destination, date, or trip type is missing. This keeps incomplete searches out of the tool layer.

2. Passenger extractor

After a booking session is open, the user may answer one field at a time or provide a whole sentence. The passenger extractor turns that message into a patch.

jsonpassenger patch
{
  "passenger_patch": {
    "given_name": "Alex",
    "surname": "Chen",
    "nationality": "CN",
    "gender": "male",
    "dob_day": "09",
    "dob_month": "10",
    "dob_year": "1997",
    "email": "alex@example.com",
    "phone": "+1 5550101234"
  }
}
One-value replies If the primitive asks "What is the passenger's surname?" and the user replies only "Jin", the session state should assign that value to the current field directly. Do not force users to write structured JSON.

Session model

A booking session stores two things:

  • Collected user data: fields such as name, nationality, DOB, email, and phone.
  • Live browser state: the Playwright page opened at the selected booking URL.

The public session API is intentionally small:

EndpointPurpose
POST /invokeSearch flights from natural language.
POST /sessions/openOpen a selected booking URL and create a browser session.
POST /sessions/{id}/messageProcess a user reply, update collected fields, and advance the booking flow.
POST /sessions/{id}/continueTry to continue from the current browser step.
DELETE /sessions/{id}Close the browser and clear session memory.
Do not trust frontend state The backend session should be the source of truth for collected fields. The frontend may display fields, but it should not overwrite backend session state with stale data.

Browser actuator

The browser actuator is the deterministic part of the primitive. It is responsible for opening the page, detecting the current step, filling fields, clicking predictable buttons, and stopping at real decision points.

Step detection

Do not rely only on page text. Use a combination of DOM selectors and text markers.

pythonstep detection sketch
def detect_step(page):
    text = read_page(page).lower()

    if "price has increased" in text:
        return "confirmation"

    if "pay with" in text or "billing details" in text:
        return "payment"

    if passenger_form_present(page):
        return "passengers"

    if "continue with saver" in text:
        return "fare"

    return "unknown"

Filling fields

For important fields, use exact selectors first and fallback selectors second. After filling, dispatch input/change/blur events so React-controlled fields notice the value.

pythonfield fill sketch
def fill_given_name(page, value):
    loc = page.locator('input[name="passengers.0.firstname"]').first
    loc.scroll_into_view_if_needed()
    loc.click()
    loc.fill(value)
    loc.evaluate("""
      (el) => {
        el.dispatchEvent(new Event('input', { bubbles: true }));
        el.dispatchEvent(new Event('change', { bubbles: true }));
        el.dispatchEvent(new Event('blur', { bubbles: true }));
      }
    """)

Phone numbers

Phone numbers often have two UI controls: country code and national number. Preserve the user's country code, then split it before filling the page.

python
def split_phone(value):
    # "+1 5550101234" -> ("+1", "5550101234")
    match = re.match(r"^\s*(\+\d{1,3})[\s\-().]*(.*)$", value)
    if not match:
        return None, re.sub(r"\D+", "", value)
    return match.group(1), re.sub(r"\D+", "", match.group(2))

Decision points

The actuator should not silently accept every page. Price increases, payment selection, and any expensive add-on should stop and ask the user.

Human confirmation If Kiwi says the price increased from one amount to another, the primitive should ask: "Reply continue to accept the new price, or back to search again." This is not a place for autonomous guessing.

2. Build an LLM JSON client

The primitive depends on structured LLM outputs. The client should strip markdown fences and recover the first JSON object if the model adds extra text.

pythoncommon/ollama_client.py
import json, re, requests
from typing import Any

class OllamaClient:
    def __init__(self, base_url="http://localhost:11434", model="qwen3:8b", timeout=120):
        self.base_url = base_url.rstrip("/")
        self.model = model
        self.timeout = timeout

    def generate_json(self, system_prompt: str, user_prompt: str, history=None) -> dict[str, Any]:
        messages = [{"role": "system", "content": system_prompt}]
        if history:
            messages.extend(history)
        messages.append({"role": "user", "content": user_prompt})
        r = requests.post(
            f"{self.base_url}/api/chat",
            json={"model": self.model, "messages": messages, "stream": False},
            timeout=self.timeout,
        )
        r.raise_for_status()
        raw = r.json()["message"]["content"].strip()
        return self._parse_json(raw)

    @staticmethod
    def _parse_json(raw: str) -> dict[str, Any]:
        raw = raw.strip()
        if raw.startswith("```"):
            raw = raw.replace("```json", "```").split("```")[1].strip()
        try:
            return json.loads(raw)
        except Exception:
            match = re.search(r"\{.*\}", raw, flags=re.S)
            if not match:
                raise ValueError(f"LLM did not return JSON: {raw[:300]}")
            return json.loads(match.group(0))

3. Implement deterministic tools

The LLM chooses a tool, but the tool code owns validation, API calls, and result normalization. Every result should include enough stable fields for the frontend and the booking session.

pythonkiwi_tools.py
import os, json, http.client
from urllib.parse import urlencode

RAPIDAPI_HOST = "kiwi-com-cheap-flights.p.rapidapi.com"
KIWI_BASE = "https://www.kiwi.com"

def _get(path: str) -> dict:
    key = os.getenv("RAPIDAPI_KEY", "")
    if not key:
        return {"error": "RAPIDAPI_KEY is not set"}
    conn = http.client.HTTPSConnection(RAPIDAPI_HOST)
    conn.request("GET", path, headers={
        "x-rapidapi-key": key,
        "x-rapidapi-host": RAPIDAPI_HOST,
    })
    raw = conn.getresponse().read().decode("utf-8")
    conn.close()
    return json.loads(raw)

def _build_query(**kwargs) -> str:
    return urlencode({k: v for k, v in kwargs.items() if v not in (None, "")})

def _parse_itineraries(raw: dict) -> dict:
    if "error" in raw:
        return raw
    flights = []
    for idx, item in enumerate(raw.get("itineraries", [])[:10], 1):
        booking_url = ""
        try:
            rel = item["bookingOptions"]["edges"][0]["node"]["bookingUrl"]
            booking_url = KIWI_BASE + rel
        except Exception:
            pass
        price = item.get("price", {}).get("amount", "N/A")
        flights.append({
            "option": idx,
            "price_usd": price,
            "provider": "Kiwi.com",
            "booking_url": booking_url,
            "raw": item,
        })
    return {"status": "ok" if flights else "no_results", "count": len(flights), "flights": flights}

def search_oneway(origin: str, destination: str, date: str, adults: int = 1, currency: str = "usd") -> dict:
    import datetime
    ts = int(datetime.datetime.strptime(date, "%Y-%m-%d").timestamp())
    query = _build_query(
        source=f"Airport:{origin.upper()}",
        destination=f"Airport:{destination.upper()}",
        outboundDepartDateFrom=ts,
        outboundDepartDateTo=ts + 86399,
        adults=adults,
        currency=currency,
        locale="en",
        transportTypes="FLIGHT",
        limit=10,
    )
    return _parse_itineraries(_get(f"/one-way?{query}"))

TOOL_REGISTRY = {"search_oneway": search_oneway}

def call_tool(tool_name: str, args: dict) -> dict:
    if tool_name not in TOOL_REGISTRY:
        return {"error": f"Unknown tool: {tool_name}"}
    return TOOL_REGISTRY[tool_name](**args)

4. Implement the browser actuator contract

The full selector implementation is site-specific, but the class contract should be stable. The server only needs these methods.

pythonbrowser_booking.py
from playwright.sync_api import sync_playwright

class BookingSession:
    def __init__(self, booking_url: str, headless: bool = True):
        self.booking_url = booking_url
        self.headless = headless
        self.pw = None
        self.browser = None
        self.page = None

    def open(self) -> dict:
        self.pw = sync_playwright().start()
        self.browser = self.pw.chromium.launch(headless=self.headless)
        self.page = self.browser.new_page()
        self.page.goto(self.booking_url, wait_until="domcontentloaded", timeout=60000)
        return self.snapshot_status()

    def snapshot_status(self) -> dict:
        text = self.page.locator("body").inner_text(timeout=5000).lower()
        step = "unknown"
        if "pay with" in text or "billing details" in text:
            step = "payment"
        elif "price has increased" in text:
            step = "confirmation"
        elif "passenger" in text:
            step = "passengers"
        return {"step": step, "url": self.page.url}

    def next_question(self, collected: dict) -> dict | None:
        status = self.snapshot_status()
        if status["step"] == "payment":
            return None
        required = [
            ("given_name", "What is the passenger's given name as shown on the passport?"),
            ("surname", "What is the passenger's surname as shown on the passport?"),
            ("nationality", "What is the passenger's nationality?"),
            ("dob_year", "What is the passenger's birth year?"),
            ("email", "What contact email should be used for booking updates?"),
            ("phone", "What contact phone number should be used?"),
        ]
        for field, question in required:
            if not collected.get(field):
                return {"field": field, "question": question, "status": status}
        return {"field": None, "question": "", "status": status}

    def apply_collected_fields(self, collected: dict) -> dict:
        # Fill page fields here with exact selectors and event dispatch.
        # Example:
        # self.page.locator('input[name="passengers.0.firstname"]').fill(collected["given_name"])
        return self.snapshot_status()

    def continue_if_possible(self) -> dict:
        # Click safe "continue" buttons, skip optional add-ons, and stop at payment/confirmation.
        return self.snapshot_status()

    def close(self):
        if self.browser:
            self.browser.close()
        if self.pw:
            self.pw.stop()
Threading detail If you use Playwright's sync API inside FastAPI, run all Playwright operations for each session in a dedicated worker thread. This avoids the "Sync API inside asyncio loop" error and keeps each page bound to one execution thread.

5. Wire the primitive server

The server is the primitive boundary. It owns the LLM controller prompts, tool calls, session registry, collected fields, and HTTP responses.

pythonserver.py
import os, re, uuid
from concurrent.futures import ThreadPoolExecutor
from typing import Any, Callable, TypeVar
from dotenv import load_dotenv
from fastapi import FastAPI, HTTPException

from common.ollama_client import OllamaClient
from common.schemas import InvokeRequest, InvokeResponse, OpenBookingRequest, BookingMessageRequest, BookingSessionResponse
from kiwi_tools import call_tool
from browser_booking import BookingSession

load_dotenv()
PRIMITIVE_NAME = "BookingPrimitiveModel"
app = FastAPI(title=PRIMITIVE_NAME)
T = TypeVar("T")

SEARCH_SYSTEM_PROMPT = """
You are BookingPrimitiveModel. Choose exactly one action.
Available tool: search_oneway(origin, destination, date, adults, currency).
Use IATA airport codes and YYYY-MM-DD dates.
If required information is missing, ask a short follow-up question.
Return JSON only:
{"decision":"ask_user|use_tool","tool":"search_oneway|","question":"","args":{}}
""".strip()

PASSENGER_SYSTEM_PROMPT = """
Extract passenger fields explicitly provided by the user.
Fields: given_name, surname, nationality, gender, dob_day, dob_month, dob_year, email, phone.
Return JSON only: {"passenger_patch":{}}
""".strip()

def llm() -> OllamaClient:
    return OllamaClient(os.getenv("OLLAMA_BASE_URL", "http://localhost:11434"), os.getenv("OLLAMA_MODEL", "qwen3:8b"))

class BookingSessionRunner:
    def __init__(self, booking_url: str, headless: bool):
        self.booking_url = booking_url
        self.headless = headless
        self.session = None
        self.executor = ThreadPoolExecutor(max_workers=1)

    def open(self) -> dict[str, Any]:
        def _open():
            self.session = BookingSession(self.booking_url, self.headless)
            return self.session.open()
        return self.executor.submit(_open).result()

    def run(self, fn: Callable[[BookingSession], T]) -> T:
        return self.executor.submit(lambda: fn(self.session)).result()

SESSIONS: dict[str, BookingSessionRunner] = {}
COLLECTED: dict[str, dict[str, Any]] = {}

@app.post("/invoke", response_model=InvokeResponse)
def invoke(req: InvokeRequest):
    plan = llm().generate_json(SEARCH_SYSTEM_PROMPT, req.query, req.history)
    if plan["decision"] == "ask_user":
        return InvokeResponse(primitive=PRIMITIVE_NAME, decision="ask_user", answer=plan["question"])
    result = call_tool(plan["tool"], plan["args"])
    return InvokeResponse(
        primitive=PRIMITIVE_NAME,
        decision="use_tool",
        extracted_args={"tool": plan["tool"], **plan["args"]},
        api_result=result,
        answer=f"Found {result.get('count', 0)} option(s). Choose one to start booking.",
    )

@app.post("/sessions/open", response_model=BookingSessionResponse)
def open_session(req: OpenBookingRequest):
    sid = uuid.uuid4().hex[:12]
    runner = BookingSessionRunner(req.booking_url, req.headless)
    status = runner.open()
    SESSIONS[sid] = runner
    COLLECTED[sid] = {}
    q = runner.run(lambda s: s.next_question(COLLECTED[sid]))
    return BookingSessionResponse(primitive=PRIMITIVE_NAME, session_id=sid, status=status, collected={}, question=q, answer=(q or {}).get("question", "Booking page opened."))

@app.post("/sessions/{session_id}/message", response_model=BookingSessionResponse)
def session_message(session_id: str, req: BookingMessageRequest):
    if session_id not in SESSIONS:
        raise HTTPException(status_code=404, detail="Unknown session_id")
    collected = COLLECTED[session_id]
    patch = llm().generate_json(PASSENGER_SYSTEM_PROMPT, req.message).get("passenger_patch", {})
    for k, v in patch.items():
        if v:
            collected[k] = str(v).strip()
    runner = SESSIONS[session_id]
    q = runner.run(lambda s: s.next_question(collected))
    status = runner.run(lambda s: s.apply_collected_fields(collected)) if q is None or q.get("field") is None else q["status"]
    if q is None or q.get("field") is None:
        status = runner.run(lambda s: s.continue_if_possible())
        q = runner.run(lambda s: s.next_question(collected))
    answer = (q or {}).get("question") or "Reached payment or the next manual confirmation step."
    return BookingSessionResponse(primitive=PRIMITIVE_NAME, session_id=session_id, status=status, collected=collected, question=q, answer=answer)

Walk-through

  1. User searches for a flight. The frontend sends the user's text to /invoke. The LLM planner selects search_oneway or search_roundtrip and returns structured arguments.
  2. The primitive returns flight options. The flight API parser normalizes price, stops, baggage, legs, and booking URL. The frontend renders each option with a "Book this option" action.
  3. User selects an option. The frontend calls /sessions/open with the selected booking URL. The backend opens the browser and detects the first checkout step.
  4. The primitive asks for missing information. If passenger name, nationality, DOB, email, or phone is missing, the session asks one direct question. The user can answer with a short value or a full sentence.
  5. The browser actuator fills the checkout page. Once required fields are collected, Playwright fills the page, selects no checked baggage, selects no insurance, advances fare and seat steps, and stops at payment or confirmation.
  6. The primitive stops at payment. Payment is a manual step. The primitive should not enter credit card details or click final purchase buttons unless the product explicitly supports that and the user has confirmed.

Build your own booking primitive

To build a booking primitive, start from the booking boundary rather than from the website UI. The primitive should own the search intent, selected option, collected passenger data, live browser session, and stopping rules.

  1. Define the booking intent. Write the fields the LLM must extract: origin, destination, dates, passenger count, cabin class, budget, baggage preference, and follow-up questions.
  2. Create one tool layer. Implement deterministic functions such as search_oneway, search_roundtrip, and open_booking_page. The LLM should choose from known tools, not call arbitrary URLs.
  3. Normalize results. Return stable fields like option_id, price, carrier, legs, baggage, and booking_url.
  4. Model the checkout session. Store collected fields and browser state server-side. Do not rely on frontend state as the source of truth.
  5. Write exact selectors first. Use stable attributes such as name, data-test, autocomplete, and accessible labels before fuzzy text matching.
  6. Define stop conditions. Price changes, cancellation policies, payment, and irreversible actions should ask the user.
  7. Expose a small API. Keep /invoke for search and /sessions/* for the stateful workflow.

Design principles

PrincipleMeaningPractical test
LLM for language The LLM extracts intent, normalizes user replies, and asks follow-up questions. Can users answer naturally instead of writing JSON?
Code for execution Selectors, field filling, and page transitions are deterministic and testable. Can the same collected data produce the same browser actions twice?
Backend-owned state The server stores collected fields and browser sessions. Can a stale frontend render fail without corrupting the session?
Human confirmation The primitive stops when money, policy, or irreversible actions are involved. Does a price increase ask the user before continuing?

  • The LLM planner can ask follow-up questions when required search fields are missing.
  • Flight API parsing returns normalized, frontend-friendly results.
  • Booking sessions are stored on the backend and cleaned up when closed.
  • Playwright operations run in a stable execution context, not directly inside an async event loop.
  • The passenger extractor supports both one-field replies and full-sentence replies.
  • Phone numbers preserve country code and split it from the national number when filling the page.
  • Each browser step has a screenshot and structured status.
  • The primitive stops for price increases, payment, and ambiguous confirmations.
  • Real API keys and user identity data are never committed to the repository.
